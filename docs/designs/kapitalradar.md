## Problem Statement

Asked how he learned about rounds at TX Ventures, Remo typed "News articles, manual research of startup websites etc, checking accelerators and pitch events etc" and also picked two listed options: "Network + startupticker" and "Dealroom / Crunchbase". None of these reads the Swiss Official Gazette of Commerce (SHAB), the one place where every capital increase of a Swiss AG must be published by law.

In the UK, Beauhurst built a business on the equivalent filings and reports that 65% of UK equity deals in 2020 were never announced ([Beauhurst](https://www.beauhurst.com/blog/all-the-data-on-unannounced-fundraisings/)). In Switzerland, Prospex already publishes daily rankings of raw SHAB capital increases (repeat raisers, the largest raises), aimed at B2B sales prospecting. What does not exist publicly is a system that **classifies which capital increases are venture financings, shows its evidence, and publishes a measured error rate**. That is Kapitalradar's gap.

The project has a second purpose of equal weight: it is a public repo that proves Remo's fit for AI builder, software engineer and product engineer roles. In his words: "As it is a public repo, the code and organization and tests etc should be there too to prove my fit for an AI builder / software engineer role too."

## What Makes This Cool

- **Rewind.** Pick any past date and see what had been published by then, classified by the pinned model. How often a "likely financing" later becomes a "confirmed round" is something the data spike measures. The demo is built around whichever story the data supports: gazette-first rounds, or rounds that were never announced.
- **Unannounced rounds with receipts.** Every company page links to the gazette entry, lists the rule hits and the model's score, and states what the gazette cannot tell you (lead investor, round size).
- **The evaluation is part of the product.** Precision bounds, recall and the rules-only baseline sit at the top of the page. Misses and rejections get their own page.

## Premises

Agreed; #2 and #3 were revised after the cross-model review.

1. **The edge is completeness, not speed.** The gazette is the most complete public record of Swiss venture rounds, unannounced ones included. "Earlier than the press" is not a claim the product makes.
2. **Filtering is the product, and the evaluation says only what it can prove.** Rules plus a Claude classifier sort capital changes into *capital increased* or *likely financing*, or abstain. Metrics are defined in the table below and published with counts, whatever they show.
3. **Prediction is a hypothesis, not a v1 feature.**
   - A capital band can authorize increases for up to 5 years, so adopting one signals readiness rather than an imminent round.
   - Precursor filings are not unique to Switzerland: UK companies file resolutions authorizing share allotments and notices varying class rights. Kapitalradar's precursor angle is therefore *untested signal value*, not exclusive data.
   - v1 at most ships a descriptive stat with a comparison group (a stretch goal). A real backtest comes after v1.
4. **Hiring is a VC-facing signal, as a stretch goal.** If time remains, financed companies on a known ATS show their open-role count. Using this for job seekers and for Remotli's company discovery belongs in Remotli's own planning.
5. **Two audiences, two surfaces.** The website serves a Swiss VC partner: rounds registered this week, evidence, rewind. The repo serves a hiring manager: module boundaries, typed schemas, tests, an eval harness in CI, ADRs, and a README led by the eval table.
6. **Company-level data only.** No natural-person data is published or committed. Every entry links to the official gazette publication. SHAB reuse terms are checked before the repo or site goes public.

### Data model (time is a first-class column)

| Table | Holds | Visibility at `asOf` |
|---|---|---|
| `publications` | Immutable raw snapshots: SHAB id, publication number, rubric, language, `published_at` (Postgres `date`: the SHAB publication day, Swiss calendar; eng delta A14), raw XML, `ingested_at` | `published_at <= asOf` (asOf is a date, inclusive) |
| `events` | Typed legal events parsed from publications, each with a `legal_date` (the statute-change date in the text, e.g. "Statutenänderung: 29.09.2026", else the journal date): capital change (nominal before/after, share counts, nominal per share, share classes), GmbH→AG conversion, capital-band adoption, formation (founding date, purpose), cancellation | Through its publication's `published_at`. Rebuilt per release (no in-place versioning in v1; CEO review X3) |
| `assessments` | Classification of one event version: tier (`capital_increased` / `likely_financing` / `abstain`), rule hits, rules-only score, Claude score, model id, prompt version, input hash, `assessed_at` | Through its event's `published_at`, which is valid because features only use data published on or before that date (see the feature rule). Each release has exactly one classifier (`model id + prompt version`), recorded in the release metadata (CEO review X3) |
| `confirmations` | External evidence: source URL, `published_at` (`date`), stated amount and stage, matched UID, match method, `match_confidence` (high / low) for the company match, `event_match` (accepted / rejected / uncertain) for the transaction and `reviewed_at` (eng delta Q7, V10), matched event id | `published_at <= asOf` |
| `companies` | UID only; display names come from name-change events, folded as of asOf (eng A3) | Always. All other company attributes (legal form, canton, founding date, purpose) are **folded from events visible at the relevant date**, never stored as current state |

- **Release isolation (eng V3, D5):** a `releases` table, with `release_id` on every derived row (events, assessments, confirmations, company names). A `current_release` pointer is flipped in one transaction after the gates pass, so a failed build never changes what visitors see. Raw publications are shared and immutable, and rollback re-points to the previous release. `releases.snapshot_date` is the last SHAB publication date a release covers: the one definition behind the default `asOf`, its upper clamp, the freshness line and "Latest available record" (eng delta A14). Indexes lead with `release_id` (eng delta P3). Each release stores its classification config in `releases.config` (rule ids, weights, τ and τ_low, display sentences, prompt version), and evidence renders from that snapshot (eng delta V14).
- **One ingestion timestamp name:** `ingested_at`.
- **Honest claim for rewind:** it shows what was **published** by that date, classified by the release's classifier. That is not what Kapitalradar had fetched at the time. The URL carries `asof`, and every page shows the release id and date. A shared link reproduces the same view while that release is live; a new release may reclassify, and the methodology page says so (CEO review X3).
- **The confirmed tier is derived at read time, never stored as an assessment.** A ledger row shows "Confirmed round" when a confirmation visible at `asOf` is matched to that event with `event_match = accepted` (eng delta V10). If the matched event was rejected or abstained, the row reads "Confirmed round · missed by classifier" and the eval counts it as a miss.
- **Abstain** displays as "Capital increased · undecided" (tier-1 styling plus a marker).
- **Cancellations and corrections** are publications too. In v1 they are discovered at release build time, because the per-candidate history fetch returns all of a company's publications up to the snapshot (CEO review X3/X4). A correction published on or before asOf supersedes the original event's fields from its `published_at`; it is stored as a new event with a `corrects` link and assessed at build (eng A4). From the cancellation's `published_at` onward, views hide the cancelled publication's events. Views before that date still show them. Corrections link to the original publication number cited in their text.
- **Evidence-reference integrity** (enforced by CI): every assessment and every displayed excerpt references an existing publication id and a character span inside its text.

### Pipeline

1. **Ingest (batch release build; CEO review X3).** v1 runs the pipeline as a batch, not a daily job: `pnpm build-release` (locally or via a manual `workflow_dispatch`) produces a dated release with one classifier version. Re-run it by hand to refresh the data. Live daily ingestion is phase 2 (TODOS.md).
   - Keyword queries fetch HR02 entries for the window: DE "Aktienkapital", FR "capital-actions", plus capital-band and conversion terms; IT is a drop item.
   - Each publication is stored raw.
   - Failure visibility: the build fails loudly, and every run writes an `ingest_runs` row (counts, errors, spend, status). A release is not published if the parse-failure or classifier-error rate exceeds 5%, or if a window day with a published gazette returns zero HR02 results.
2. **Parse.**
   - Deterministic extractors produce typed events.
   - Capital **reductions** (new < old) are excluded from candidates.
   - A reduction and re-increase in the same entry ("Herabsetzung … gleichzeitige Wiedererhöhung") gets the negative rule `restructuring_pair`.
   - Set-off contributions ("Verrechnung") are parsed into a `contribution_type` field.
3. **Company history.** For every capital-increase candidate, fetch all SHAB publications for its UID (the spike verifies this works). Fallback chain: SHAB by UID → Zefix's dated publication references for that UID (never its current-state fields) → history limited to the backfill window, labeled partial. Fold them into as-of company state: founding date, legal form, purpose, prior capital band and conversion.
4. **Rules.**
   - **Pre-filter:** AG + an increase + no hard-negative hit. Hard negatives are capital reductions and `restructuring_pair` only; all other negatives are soft weights (eng Q1). Every parsed capital change gets an assessment row with rule hits and a reason, including rejects (tier `capital_increased`, no Claude score); reductions appear in company history, not in the feed (eng Q2). The pre-filter's recall is the **ceiling** for rules + Claude, and it is reported.
   - **Rules-only baseline:** a weighted score over named rules (odd nominal amounts from small-nominal shares, AG under ~6 years old, tech/biotech purpose, new preferred class; negatives: round amounts with a holding purpose, ESOP-sized increments, `restructuring_pair`, set-off-only contributions). The threshold is chosen on dev data.
5. **Classify.**
   - Claude also receives the fired rule ids and a one-line rule catalog. Cited rule ids must be a subset of the fired ids, otherwise the assessment is rejected, logged and counted as an error (eng Q3). Fields:
     - capital before/after
     - share counts and classes
     - contribution type
     - legal form
     - company age bucket
     - canton
     - purpose text
   - **Redaction:** before it sees them, these are removed:
     - the UID
     - current and former names (DE/FR/IT)
     - natural persons
     - street addresses
     - the seat town
   - A fixture test proves the redaction works.
   - Output is Zod-validated: a score plus a rationale citing rule ids.
   - **Tier mapping:** score ≥ τ → `likely_financing`; τ_low ≤ score < τ → `abstain`; below τ_low → `capital_increased`. τ and τ_low are chosen on dev.
   - **Cost control:**
     - Idempotency key `(event_version, input_hash, model_id, prompt_version)`: an existing assessment is never paid for twice.
     - `MAX_CLASSIFICATIONS_PER_RUN` aborts the run when exceeded.
   - **Route: Remo's Claude subscription, not the paid API (decided 2026-10-05, supersedes the Batch API route of eng D3 and the batch deadline of eng delta V16).** Each classification is one headless Claude Code call: `claude -p --model claude-opus-5-5 --effort low --system-prompt-file <classifier prompt> --json-schema <output schema> --tools "" --no-session-persistence --output-format json`.
     - **Isolation:** the calls run with `CLAUDE_CONFIG_DIR` set to a dedicated config directory, logged in once to the same subscription, so no global CLAUDE.md, memory, hooks or plugins enter the prompt. `--bare` can't be used: it ignores the subscription login and accepts only an API key.
     - **Context check:** before a run, a probe call's reported input-token count must stay under a fixed ceiling, proving nothing beyond the classifier prompt was injected.
     - **Throughput:** at most 3 concurrent calls, checkpointed by the idempotency key. On a usage-limit error the run stops cleanly and resumes later. The backfill starts as soon as the prompt and τ are frozen; day 2 fills the wait with work that doesn't need classifications (as-of queries, leak tests, UI against fixtures).
     - **Measure first:** run 100 items and record how much subscription usage they consume before the full backfill. The build sessions draw on the same limits during the 3 days.
     - The CLI call sits behind a small `ClassifierBackend` interface, so an API-key backend can be added later. The "cost per 100 publications" metric reports the API-equivalent cost from the token counts in the JSON output.
6. **Feature rule.** Features for an event read only rows published on or before that event's `published_at`. A CI test builds features with and without future rows injected and asserts identical output.
7. **Backfill (eng A1, A2).** From 2025-08-01 to the release snapshot, plus the company-history fetch per candidate. It runs locally as resumable, rate-limited batches (concurrency ≤ 4, exponential backoff, a checkpoint table), with publication bodies cached by id in `publications` (immutable). Each tracked company's publication list is refetched on every release build, so later corrections, cancellations and renames are picked up (eng V5). The spike measures latency and rate limits.

### Labels and evaluation

- **Unknowns in precision (eng T3):** a sampled positive is never dropped; unknown and unverifiable items enter the weighted bounds. The unknown exclusion below applies only to dev and recall-cohort labels.
- **Positive class:** startup relevance = *yes* AND transaction type = *new equity financing*. Precedence (eng V1): a positive requires new money, i.e. a cash or mixed contribution in the same capital change. Set-off-only conversions are `conversion_only` and **not** positive in v1, even when they create a new preferred class; a convertible converting alongside new money is positive. *Unknown* on either axis is excluded from precision and recall and reported as a count.
- **Label provenance:** every label records `text_only` or `verified` (with a source URL). Published precision uses only verified labels.
- **Leakage guard:**
  - The Assignment's 30 entries and the spike's ~20 matched companies are **dev-only**. Together, labeled on both axes, they form the dev set: 30 + the matched spike rounds (about 12–20, depending on the spike's hit rate, so about 42–50 in total). No further dev labeling.
  - Partition by UID before any inspection (eng V4). An inspected-company ledger (Assignment, spike, X1 claim check, any ad hoc lookup) is excluded from the holdout, and cohort draws are grouped by company so one company's rounds never cross partitions.
  - The recall cohort is pre-registered as a list of announced rounds (seeded draw, committed before the spike), but its gazette entries stay **sealed** (not opened, not used for rule design) until the rules and τ are frozen.
  - The precision sample is drawn **after** the freeze, from holdout positives of companies nobody inspected.
  - The recall cohort excludes spike companies.
- **Recall cohort, declared before the spike:**
  - startupticker rounds announced 2025-12-01 to (snapshot − 180 days), with one match window of −120/+180 days everywhere (eng A1)
  - the target entity is a Swiss AG; GmbH is out of v1
  - priced equity (grants, pure loans and debt excluded)
  - Excluded rounds are listed with reasons. Eligibility is decided before matching (registry legal form + announcement type); an eligible round without a matching event counts as a miss in both recalls (eng T4).
- **Matching:**
  - **Company match:** normalized legal name, a brand alias list, and manual review of every miss (n ≈ 30 holdout rounds, per CEO review S1).
  - **Event match:** the nearest capital-increase event published between 120 days before and 180 days after the article; more than one candidate goes to manual review (eng Q5). Every cohort match is adjudicated by hand with linking evidence (date proximity, share class, contribution type, amount plausibility); an unlinked match is "uncertain", excluded from hits and listed (eng V6).
  - **Confidence (eng Q5):** high = exact normalized legal name or UID; low = alias or fuzzy. Low-confidence matches show as "possible confirmation" and count as hits only after manual confirmation.

**System positive** (one definition, used by every row): a rules-only positive = rules score ≥ its dev threshold; a rules + Claude positive = tier `likely_financing`. Abstain counts as not positive.

**Metric table** (each number is published for **rules-only** and **rules + Claude** separately)

| Number | Population | Sampling | Notes |
|---|---|---|---|
| Recall | Recall cohort (holdout only) | Seeded random draw of 30 from the eligible non-spike rounds; seed and list committed before the spike (CEO review S1) | Detected = system positive (defined above). The eval code never reads `confirmations`, and a test enforces that. Abstain = not detected |
| Pre-filter recall | Same cohort | All | The ceiling for both systems |
| Precision | Holdout positives of each system | One seeded sample of n = 30 from the union of both systems' holdout positives (CEO review S1, S1b), stratified by both / rules-only only / Claude only, with at least 10 per system. Precision is weighted by stratum population (CEO review X2), with boundary-safe per-stratum Wilson intervals combined for the weighted estimate instead of a bootstrap (eng V7). Sampling uncertainty is reported separately from the unverifiable-label bounds; each system's n is shown | Report verified / refuted / unverifiable counts, and precision as bounds (unverifiable counted as false and as true) |
| Abstention rate | All holdout candidates | All | — |
| Cost per 100 publications | Holdout run | All | From token counts |

The dev set (Assignment + matched spike rounds; CEO review S1, full size in TODOS.md) is used for **rule design, τ selection and the model memory test only**. It is never reported as precision or recall. The recall cohort is 30 holdout rounds.

**Model memory test (dev data).** Score the announced dev rounds with and without names.
- **Pass:** mean |Δscore| < 0.05 and at most 1 tier flip across the announced dev rounds (n ≈ 12–20).
- **Fail:**
  - publish the measured effect in the methodology strip
  - report holdout metrics separately for events published after the model's training cutoff
- **Model (eng review D3):** `claude-opus-5-5` at low effort, run on Remo's subscription through headless Claude Code (route above; no API spend), with usage measured on 100 items first. Its training cutoff (Jun 2026) overlaps the cohort, so a post-cutoff split is impossible. Memory risk is handled by redaction plus the identifiability probe, and the methodology page discloses it.

### UI (`app/`)

Screen, state, status, responsive and accessibility specs are in "Design Review (working)" below (approved D3–D7). The bullets here are the canonical summary.

- **First screen, in order (design IA3):**
  1. Wordmark + descriptor: "Swiss capital increases, classified with evidence from the official gazette."
  2. One curated link (design D5): "Try a rewind: <company> on <date>, N days before the round was announced ↗", picked after the spike from inspected companies only (X1 or spike evidence; never the sealed cohort or holdout). Wording follows the spike's story. The README GIF uses the same case.
  3. The **"Published by <date>"** control, the visual anchor, with "release <id> · data as of <date>" beside it.
  4. One mono eval line: "Release evaluation · <eval date> · does not rewind · rules + Claude: precision a–b (n=<this system's sample>), recall x/<cohort size> announced rounds · rules-only: … → Methodology". The full metric table is only on /methodology.
  5. Window heading "Published 21–27 Sep 2026" with counts, the filters, the rows.
- **Date model (design IA1):** `asOf` accepts any calendar date. It defaults to the **release snapshot date**, is clamped to [backfill start, snapshot date] with a visible notice, and a malformed value redirects to the default with a notice. "Latest available record · <date>" is the reset link everywhere.
- **Feed (design D7):** the Monday–Sunday week (Europe/Zurich) containing `asOf`, capped at `asOf`, newest SHAB publication first, with "← previous week · next week →" links. Default filter: likely financing + confirmed round; below the rows one line, "52 other capital increases published this week ▸", opens all statuses. Filters are multi-select and live in the URL.
- **Ledger row (in the feed; design AS2, IA2):** a table row with no box. Columns: company (name; canton · purpose), status (pips + label), "Nominal share capital (CHF)" before → after, new shares as % of post-step shares, "Announced round" ("—", or a stated amount with its source link when a confirmation visible at `asOf` has one and its event match is accepted), "SHAB published <date>", and the SHAB link. The company name and the SHAB link are separate links.
- **Company page (CEO review E1, design IA6):** the route `/c/[uid]?asof=…` (same `asof` as the feed; release id shown) is **one chronological record**:
  - a summary block: name as of `asOf`, UID, legal form, canton, founding date, and "Amount raised / Lead investor: not in the SHAB"
  - the coverage line under the heading
  - entries oldest first, ending at a red `asOf` cut line with the "Latest available record" link and no count of later events, because the count itself would leak the future. Over 12 entries, the oldest collapse behind "Show N earlier entries".
  - Each capital event carries its capital history figures, status, the evidence block and its SHAB link; confirmations are their own dated entries with match confidence.
  - **Evidence block (design ST2):** rule hits as plain sentences next to the field that fired them (display strings live in the rule catalog); "Classifier score 0.86 · likely-financing threshold 0.xx · not a calibrated probability"; until OQ1 clears, the excerpt slot reads "Excerpt withheld until the gazette's reuse terms are confirmed · Read on SHAB ↗".
  - A UID with no SHAB publication by `asOf` gets the same 404 as an unknown UID, identical in status and body, so a rewound view never reveals that a company appears later (eng delta A11).
  - Built from the per-candidate history fetch, with no new data source. Tests: share-issuance math and as-of.
  - **A step** is any capital-change event, reductions and `restructuring_pair` included, ending at `asOf`. Each shows nominal capital before/after, share counts, and share issuance (new shares as % of post-step shares; not investor dilution).
  - **No share-issuance figure** when share counts are missing, the nominal value per share changes (a split), or the step reduces or cancels and reissues shares (reductions, `restructuring_pair`). It shows as "—" with the reason, and such steps list shares cancelled and shares issued instead.
  - **Multiple share classes:** share issuance uses total shares across classes, and the classes are listed. This is a share-count measure, not investor dilution or economic ownership (CEO review X5).
  - **GmbH→AG conversion:** shown as its own step, with no share-issuance figure.

```
  eval/ (offline): labels, sealed cohort, cached model outputs ──> README metric table
  export job (E6): events + tiers ──> CSV/JSON + data card (not exposed until OQ1)
```

- **Boundaries:** one writer (the Actions job) and one reader (the web app, through a read-only DB role); eval and export run offline. The coupling is justified: the store is the single contract between the jobs and the web app.
- **Single points of failure:**
  - SHAB API availability: covered by daily retry plus the anomaly alert.
  - The Actions schedule: covered by keepalive plus failure email.
  - The Neon database.
  - The Claude API: covered by the spend cap, abstain and the error-rate alert.
- **Scale:** about 500 HR02 publications a day and about 15 classifications a day. 10x and 100x load hit the backfill history fetch first (R2-20), not the runtime.
- **Security architecture:** a public read-only site with no write endpoints. The only privileged surfaces are the Actions secrets (Anthropic key, Neon URL) and the private preview (R2-27).
- **Rollback:** Vercel instant rollback for the app. Additive migrations only. A bad classifier version is rolled back by re-pinning the production `model + prompt version`; history is kept because assessments are append-only.
- **Fit of the selective expansions:** E1 reads the same events and adds no coupling. E6 reads the same tables offline. Neither changes the architecture.
- **What makes it obvious to a new engineer:** the README diagram above plus one ADR on the as-of rule.
- **Platform potential:** the same store later serves the backtest, the digest, Ask and an API.
- **WARNING (YAGNI):** versioned event rows plus versioned assessments plus URL pins is a lot of machinery for a 3-day build. Implementation owner (/plan-eng-review) must prove each versioning layer is needed in v1, or simplify it (R2-1, R2-14, R2-15, R2-16).

### Section 4: Data Flow & Interaction Edge Cases

```
  SHAB XML ──> VALIDATE (XSD-shaped Zod) ──> PARSE (typed events) ──> PERSIST (upsert by SHAB id) ──> CLASSIFY ──> READ (asOf)
     │ nil/empty: zero results ──> anomaly check (weekday + gazette published) [R2-29]
     │ wrong shape: Zod fail ──> parse-failure counter, alert >5%, raw kept
     │ timeout/5xx: retry w/ backoff ──> job fails loudly after N
     │ duplicate/rerun: idempotent upsert; assessment reuse on input hash
     │ encoding: Swiss apostrophe thousands (132'231.38), FR spacing (1 234,50) ──> fixtures per language
     │ stale/partial: late publication with old published_at ──> visible in old asOf views (disclosed)
```

**Async ordering.** Invariant: one assessment per (event, input hash, model, prompt version), and no as-of view shows rows published after asOf.
- Daily run vs backfill run: both write `assessments`. The concurrency group serializes them. The unique key prevents a double write if they overlap anyway.
- Re-parse vs classify: a new event version can be created while the old version is being classified. Owner must prove assessments reattach by input hash (R2-15) and that confirmations reference the stable logical id (R2-16).
